# แผนทดสอบ guard ก่อน LLM ของทางรอด

ทดสอบการเลือกเจตนา การใช้ข้อมูลจากสี่บริการ และการถามเฉพาะข้อมูลที่จำเป็น ตาม [สเปก guard](thang-rot-guard-spec.md) ชุดทดสอบใช้โปรไฟล์จำลองและตัวแทน LLM ในเครื่อง

## ผลก่อน DEV แก้ Guard

รันวันที่ 28 พ.ย. 2569 บนโค้ดแอปที่ HEAD `3b6d5fa` เคสที่ตกด้านล่างคือพฤติกรรมที่ทำซ้ำได้ในเครื่อง หลายเคสเกิดจากกฎเลือกคำถามข้อเดียวกัน

| ชุดทดสอบ | ผล |
| --- | --- |
| Backend ตามสเปก รวมทุกกลุ่ม | **ผ่าน 44 จาก 129 เคส ตก 85** |
| ↳ ชุดตรวจรับเดิม SRC / DATA / CHAT / SAFE | ผ่าน 39 จาก 56 ตก 17 |
| ↳ ถามจริงในแชท 16 รูปแบบการเชื่อม × 4 หัวข้อ (FLOW) | ผ่าน 4 จาก 64 ตก 60 |
| ↳ บทสนทนา การใช้โปรไฟล์ และความยินยอม (TURN) | ผ่าน 1 จาก 9 ตก 8 |
| Flutter ตามสเปกใหม่ (UI) | **ผ่าน 0 จาก 3 เคส** |
| Contract regression เดิม | ผ่าน 245 จาก 245 |
| Flutter regression หน้าแชทเดโมและโปรไฟล์ | ผ่าน 29 จาก 29 |

ทั้ง 16 รูปแบบผ่านการเติมข้อมูลเดโม ในแชทมีเพียง FLOW-01, 03, 09 และ 11 ของหัวข้อเงินว่างงานที่ผ่านการเลือกคำถาม ทุกเคสใช้บัญชีเดโมแยกกัน ค่าจ้างและเหตุออกจากงานเป็นคำตอบตั้งต้นที่มีในทุก persona ผลของ FLOW ยังต้องประกอบกับการตรวจฟิลด์ในหน้าโปรไฟล์และหลักฐานของแต่ละบริการก่อนเปิดใช้ข้อมูลจริง

## รันชุดตรวจรับซ้ำ

รันจาก root ของ repo

```powershell
node --test --test-reporter=spec contracts/test-thang-rot-guard.js
```

ชุดนี้เปิด mock server บน loopback ใช้ข้อมูลในหน่วยความจำ และใช้ตัวแทน LLM สำหรับตรวจข้อความที่ส่งออก ชุดตรวจรับรันแยกจาก `npm test` และคืน exit code 1 เมื่อผลต่างจากสเปก. [ชุดทดสอบ](../../contracts/test-thang-rot-guard.js)

รันทีละคำสั่งใน CI เพื่อให้เห็นผล backend และ Flutter แยกกัน ตัวอย่างสำหรับ PowerShell ที่เรียก `flutter` ได้จาก PATH

```powershell
npm --prefix contracts test
Set-Location app
flutter test --no-pub test/thang_rot_guard_handoff_test.dart --reporter expanded
flutter test --no-pub test/home_demo_chat_test.dart test/profile_overview_test.dart --reporter expanded
```

ชุด Flutter เปิด ChatScreen จริงและควบคุมผล API ด้วยตัวแทน จึงทดสอบได้ทั้งปุ่มที่ถูกกด เนื้อหาที่อยู่บนจอ และช่วงที่คำขอยังค้าง. [ชุดทดสอบ Flutter](../../app/test/thang_rot_guard_handoff_test.dart)

## เคสตรวจรับเมื่อ flow ใหม่พร้อม

ตั้งวันทดสอบและข้อมูลสมมติให้คงที่ ใช้ตัวแทนบริการสำหรับเคสเชื่อมข้อมูลและตั้งสถานะได้ครบ ทั้ง **ได้รับ**, **ไม่ส่งค่า**, **ล้าสมัย**, และ **ขัดกัน** แต่ละเคสตรวจคำถามที่แสดง ผลจากกฎ ค่าก่อนและหลังบันทึก และข้อความที่ส่งถึง LLM ตามที่เกี่ยวข้อง

| เคส | ตั้งต้นและสิ่งที่ทำ | ผ่านเมื่อ |
| --- | --- | --- |
| MAN-01 | เชื่อมครบ มีอายุและเขตทะเบียนบ้าน แต่ไม่มีสัญชาติ เลือกเช็กเบี้ยผู้สูงอายุ | ถามสัญชาติก่อน ข้ามอายุกับเขต และยังไม่มีการเรียก LLM ระหว่างถาม |
| MAN-02 | เชื่อมเฉพาะ ThaID กับ สปส. มี `ss33 = true` และบันทึกเหตุออกงานไว้ เลือกเงินว่างงาน | ถามค่าจ้างถ้าต้องประมาณยอด ข้ามเหตุออกงานและสมทบ สถานะข้อมูลของบริการที่เหลือไม่มีผล |
| MAN-03 | ยังไม่เชื่อม สลับทดสอบโปรไฟล์ว่างกับโปรไฟล์ที่กรอกอายุเอง เลือกเบี้ยผู้สูงอายุ | เริ่มจากอายุเมื่อไม่มีค่า และเริ่มจากเกณฑ์ข้อถัดไปเมื่อมีอายุ ทั้งสองทางไปต่อได้ |
| MAN-04 | ผู้ใช้เคยตอบค่าหนึ่ง และแหล่งข้อมูลอัปเดตค่าที่ขัดกัน ขณะกำลังตรวจรายการที่ใช้ค่านั้น | ถามยืนยันเฉพาะค่าที่ขัดกัน ผู้ใช้กดข้ามแล้วสถานะสิทธิคงเป็นต้องตรวจต่อ และไม่มีการนับยอดเพิ่ม |

### วิธีปิดงานและจัดการกรณีที่ยังทดสอบจริงไม่ได้

1. **DEV ส่งผลบน revision เดียวกัน** แนบรายงาน backend 129 เคส, Flutter 3 เคส และ regression ทั้งสองชุดหลังย้าย expectation ที่ขัดกัน รายงานต้องบอกจำนวนที่รัน ผ่าน ตก และข้าม ห้ามนับเคสข้ามหรือเคสจำลองแทนผลของระบบจริง
2. **QA เดิน MAN-01 ถึง MAN-34 บน build นั้น** ตอนนี้ยังไม่มีผลตรวจรับรายเคสครบทั้ง 34 รายการ บางส่วนมีหลักฐานจากชุดอัตโนมัติแล้ว เช่น MAN-17 จาก TURN-06 และส่วนปุ่มของ MAN-25 จาก UI-01 ให้ใช้หลักฐานซ้ำได้เฉพาะขั้นที่ตรงกัน สำหรับเคสข้อมูลขัดกัน/หมดอายุ/ตอบกลับช้า ให้ใช้ตัวแทนบริการที่ควบคุมบัญชี รุ่นการเชื่อม เวลาปัจจุบัน และจังหวะคืนผลได้ เก็บต่อเคสเป็น `caseId, revision, fixture, expected, actual, evidence, status` ระบุ `pass`, `fail` หรือ `blocked` พร้อมชื่อทีมที่ปลดล็อก หากยังไม่มีทางจำลองสถานะให้ DEV เพิ่มจุดควบคุมในสภาพแวดล้อมทดสอบ
