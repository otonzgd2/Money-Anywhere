# เปลี่ยน UI ทางรอดทั้งระบบ

อัปเดตทุกหน้าที่ผู้ใช้เปิดได้จากแอปทางรอด รวมถึงหน้ารายละเอียด หน้าย่อย กล่องโต้ตอบ และ HTML ที่แอปเปิดผ่านเบราว์เซอร์ ส่งเป็นงานชุดเดียวใน `otonzgd2/Money-Anywhere` ใช้ checkout `D:/Money-Anywhere` ซึ่งอยู่บน `main` ที่ `76e9646` ตอนเตรียม handoff ชุดอ้างอิงใหม่อยู่ใน working tree ให้ตรวจ `git status --short --branch` แล้วต่อยอดจากไฟล์เหล่านี้

## แหล่งอ้างอิง

- **DEMO หลัก** จาก `index-edited.html` ของชุดส่งวันที่ 28 พ.ย. 2569 ใช้เปิด splash และ onboarding ตั้งแต่ต้น เลือกหน้าและสภาวะข้อมูลจากแถบเครื่องมือข้างตัวอย่าง [เปิด DEMO](../mockups/index.html)
- **หน้าเริ่มและแผนตัวอย่าง** ใช้ลิงก์ลัดเพื่อเทียบ UI แบบมีข้อมูลและเริ่มทดสอบจากจุดต่าง ๆ [หน้าแรก](../mockups/index.html#home-demo) · [แผนตัวอย่างสิบหมวด](../mockups/index.html#plan-demo) · [รายละเอียดงานตัวอย่าง](../mockups/index.html?opportunityId=j2&district=บางรัก)
- **บริการรัฐ** จาก `gov-services-v2.html` ใช้เป็นแบบการ์ดสิทธิ์ รายละเอียด เอกสาร ช่องทางยื่น และสถานะ สำหรับรายการที่ระบบรองรับอยู่แล้ว [DEMO บริการรัฐ](../mockups/gov-services.html)
- **ฟอร์มสมัครงานจำลอง** เปิดจากปุ่ม **รายละเอียดงาน** ของงานตัวอย่าง ใช้หน้ากรอกข้อมูล แนบเอกสาร ตรวจทาน และใบรับจำลองจากไฟล์ใหม่ [ฟอร์มสมัครงาน](../mockups/job-application.html)
- **ภาพ โลโก้ และไอคอน** ใช้ภาพ 43 ภาพเทียบตำแหน่งและลำดับข้อมูล อ่านรายละเอียดการใช้ไอคอนและแหล่งไฟล์ภาพประกอบในรายการไอคอน [ภาพอ้างอิง](../mockups/screenshots/) · [Assets](../mockups/assets/) · [รายการไอคอน](../mockups/icon-list.md)

เมื่อแบบ HTML ไม่มีจอตรงตัว ให้ใช้หน้าที่ใกล้ที่สุดในตาราง พร้อมโครงข้อมูลและการกระทำของเส้นทางจริง ภาพ snapshot ใช้เทียบลำดับข้อมูลและหน้าตา ส่วนป้ายที่มา จำนวนเงิน สถานะ และสิทธิ์ใช้ค่าจากระบบจริงในแต่ละโหมด หน้าเอกสารภายใน ได้แก่ API reference, architecture และ pitch ไม่ใช่เส้นทางผู้ใช้ของแอป

- ใช้หัวการ์ด แถวข้อมูล ป้ายสถานะ ปุ่ม และ sheet ร่วมกันตามแบบ กำหนดสีหลัก `#0b4fd6`, หัวเข้ม `#0a3a9e`, CTA `#0a2a6b`, พื้น `#f4f7fc` และเส้นขอบ `#e6ebf2` ยึดความชัดเจนของข้อความภาษาไทย และใช้ Google Sans / IBM Plex Sans Thai ตามตัวอย่างเมื่อมีไฟล์และสิทธิ์ใช้งานบนอุปกรณ์ ใช้ฟอนต์ไทยที่แอปมีอยู่เป็น fallback รักษาแถบสถานะ Android และ safe area ของระบบ
- ใช้ API และโมเดลเดิมเป็นจุดเชื่อมข้อมูล `opportunityId`, บริบทเขต, หมวด, เนื้อหา, ค่าตอบแทน, เงื่อนไข, ช่องทาง, URL, สถานะ, ที่มาและพิกัดเป็นข้อมูล runtime เพิ่มฟิลด์แบบ optional เฉพาะเมื่อจำเป็น คงความเข้ากันได้กับข้อมูลเดิม รองรับการโหลด ค่า null ข้อมูลบางส่วน หมดอายุ และ offline ด้วยข้อมูลที่ยืนยันได้ เปิดต่อได้จากลิงก์เก่า [ขอบเขตข้อมูลกรุงเทพฯ](../mockups/bangkok-opportunity-scope.html)
- SQLite งานเดิมเปิดผ่าน `JOB_DB_FILE` และไปยัง Flutter ผ่าน API ที่มีอยู่ ถ้าไม่มี DB ให้แสดงรายการหรือสถานะว่างตามข้อมูลที่ API ส่ง ใช้พิกัดจำลองเฉพาะ DEMO ที่ระบุชัด รายละเอียดและแผนที่ใช้ข้อมูลเดียวกัน และคงสถานะบันทึกกับความคืบหน้าเมื่อผู้ใช้ย้อนกลับหรือกดซ้ำ
- คงการประเมินสิทธิ์โดยอัตโนมัติเมื่อข้อมูลพร้อม แยกยอดสิทธิ์จากรายได้งาน คงข้อเท็จจริงที่ผู้ใช้แจ้งและป้ายตรวจสอบสิทธิ์ตามที่มา หน้าสรุปเริ่มใช้งานบันทึกสถานะรับทราบของตัวเอง ใช้ consent `core`, `ai` และแหล่งข้อมูลตามสัญญาเดิม การข้ามบริการไม่เปลี่ยน consent และการต่อแบบ mock อยู่ในโหมดที่เปิดให้ใช้
- ใช้เส้นทาง Guard และ OpenAI ที่มีอยู่ รักษาเงื่อนไขงานที่ผู้ใช้บอก เขต ประเภทงาน เวลาว่าง และผลที่แสดงไปแล้ว ยืนยันกรณี **มีงานประจำแล้ว ต้องการงานเสริม** ว่าแชตตอบตามบริบทและไม่วนถามซ้ำ รวมการบันทึกแผนจากแชตโดยใช้ ID จากผลจริง [บันทึกการแก้บริบทค้นงาน](https://github.com/otonzgd2/Money-Anywhere/commit/8efb63bb57e88fcb8cfd489d155ffe9cba025401)

## เกณฑ์ตรวจรับทั้งชุด

1. ไล่ทุกแถวในตารางบน Android และ DT50 หรือ viewport เล็กใกล้เคียง ตรวจโหมดตัวอักษรใหญ่ TalkBack ลำดับ focus เป้ากด คีย์บอร์ด การเลื่อน และภาพ/ข้อความภาษาไทย ใช้ภาพเทียบสำหรับจอหลักและบันทึกเส้นทางเทียบของหน้าย่อย
2. ทดสอบเปิดครั้งแรก เชื่อมทั้งหมด/บางส่วน/ข้ามทั้งหมด กลับเข้าซ้ำ และเชื่อมล้มเหลว แล้วตรวจผลประเมินในโอกาสกับจำนวนจริงในบัญชี ทดสอบโปรไฟล์จาก ThaID แบบอ่านอย่างเดียวและการกรอกเอง รวมถึงกดยกเลิกและคืนค่าเดิมหลังตัดการเชื่อม
3. ทดสอบคีย์เวิร์ด+เขต+ประเภทงานทั้งห้าแถบ จากรายการและแผนที่ถึงรายละเอียดเดียวกัน ทดสอบมีพิกัด/ไม่มีพิกัด DB ข้อมูลว่างและหมดอายุ และกดบันทึกซ้ำ ตรวจขั้นต่อไป/ติดต่อ/สถานะของแผน และเปิด URL งานเดิมได้ทั้งประกาศจริงและ DEMO
4. ทดสอบ consent และแชตเมื่อยังไม่ได้อนุญาต เมื่อยอมรับ เมื่อถอน และเมื่อ Guard แจ้งเตือน ทดสอบงานเสริมตามบริบท การพิมพ์ การถอดเสียง/กลับไปพิมพ์ และเน็ตหลุดหรือ API ตอบช้า
5. รัน `flutter analyze` และ `flutter test` จาก `app/` รัน `npm.cmd test` จาก `contracts/` เมื่อแตะสัญญา API และ `node docs/mockups/smoke-test.js` กับ `node docs/mockups/gov-services-smoke.js` จาก root สำหรับ DEMO บันทึกผลทดสอบและสิ่งที่ยังตรวจบนเครื่องจริงไม่ได้ในสรุปส่งงาน
