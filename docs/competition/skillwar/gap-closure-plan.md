# แผนปิดช่องว่างคะแนนของทางรอด

แผนนี้ตอบข้อ 1 ของงานเตรียมแข่ง ครบทั้ง 25 เกณฑ์ใน [ใบประเมิน](scorecard.md) ฐานประเมินเดิมคือ **58/100 ก่อนหักคะแนน** เริ่มจากการทำให้เส้นทางแชตถึงบันทึกแผนบน Android ใช้ได้จริงและตรวจที่มาของผลได้ จากนั้นเก็บหลักฐานด้านความเหมาะสมของโจทย์ UX และ Pitch เกณฑ์ผ่านในเอกสารนี้เป็นเป้าตรวจรับของทีม ส่วนคะแนนตัดสินโดยกรรมการ

ใช้ตารางหลักฐานตรวจรับผลแบบผ่านทีละข้อสำหรับเป้า 100/100 ก่อนหัก [เงื่อนไขที่วัดได้และผลทดสอบล่าสุด](evidence-acceptance.md)

ใช้แผนแก้แชต 3 ชุดกำหนดจุดเปลี่ยนในโค้ดและทดสอบเส้นทางเดิมทุกครั้ง [จุดแก้และการตรวจผลกระทบ](full-score-change-plan.md)

## ลำดับงานและผู้รับผิดชอบ

| งาน | เจ้าของตามบทบาท | เริ่มเมื่อ | ผลที่ต้องได้ |
| --- | --- | --- | --- |
| A. เตรียมแหล่งข้อมูลและเคสหลัก | ข้อมูลและ QA | เริ่มได้ทันที | รายการที่ตรวจที่มาและเปิดลิงก์ได้ อย่างน้อยหนึ่งเคสค้นเจอจริง เคสเปลี่ยนเขต และเคสผลว่าง แยกประกาศออกจากช่องทางหางานภาครัฐ |
| B. ทำผลค้นหาในแชตให้ตรวจสอบและบันทึกได้ | Backend/AI และ Flutter | ได้เคสและรูปทรงข้อมูลเบื้องต้นจาก A | ข้อความไทย → ตัวกรอง → โมเดลและเครื่องมือ → การ์ดจากรายการจริง → ยืนยันบันทึก → แผนของฉัน |
| C. ตรวจเวอร์ชันเดียวบน Android | Flutter และ QA | ได้ build จาก B และรายการจาก A | ผลสองอินพุต, follow-up, กรณีผิดพลาด และเวลาซ้อม พร้อม SHA ของ APK และ backend |
| D. สรุปโจทย์ผู้ใช้ UX และ Pitch | Product/Pitch และ QA | หลักฐานปัญหาเริ่มได้ทันที ภาพและการจับเวลาใช้ผล C | เด็ค สคริปต์ 7 นาที และหลักฐานรองรับคำกล่าวแต่ละข้อ |
| E. ยืนยันงานและหลักฐานวันแข่ง | ผู้ดูแล Kiro และผู้ส่งงาน | หลังผู้จัดเปิดโจทย์และเริ่มแข่งขัน | เงื่อนไขโจทย์ขยาย, Activity Log จริง, repo ส่งงาน, วิดีโอสำรอง และผลซ้อมของ build วันนั้น |

ถ้ามี 3 คน ให้ Backend/AI รับหน้าที่ Kiro, Flutter รับอุปกรณ์ และ Product/Pitch รับข้อมูลกับการส่งงาน ให้คนที่ไม่ได้ขับเครื่องเป็นผู้จับเวลาและลงผล QA

## A. เลือกข้อมูลที่แสดงต่อกรรมการได้

- [ ] เลือกเส้นหลักหนึ่งเส้นสำหรับคนกรุงเทพฯ ที่รายได้ลดและกำลังหางานใกล้บ้าน เริ่มด้วยคำขออิสระที่มีเขต เวลา หรือทักษะ จบที่แผนที่จะลงมือทำ เก็บผลค้นหาจริงก่อนเลือกข้อความซ้อม
- [ ] เจ้าของข้อมูลเปิดลิงก์ต้นทางทุกระเบียนที่จะโชว์ บันทึก ID, ชื่อ, เขตหรือรูปแบบทำงาน, เจ้าของข้อมูล, วันตรวจ, วันปิดรับถ้ามี, URL, และเหตุผลที่ใช้หรือเผยแพร่ได้ ตรวจอีกครั้งในวันแข่ง
- [ ] เลือกประกาศหรือโอกาสจริงที่ยังใช้ได้สำหรับเคสค้นเจอ ข้อมูลสวัสดิการและลิงก์บริการสาธารณะใช้เป็นทางลงมือทำได้ตามประเภทของข้อมูล หากมีเพียงลิงก์กรมการจัดหางาน ให้ขึ้นเป็น “ช่องทางค้นงาน” และเก็บสถานะเคสประกาศจริงเป็นรอตรวจ
- [ ] เตรียมเคส A ที่ค้นเจอ เคส B ที่เปลี่ยนเขตหรือทักษะหนึ่งปัจจัย และเคส C ที่คาดว่าจะไม่มีผลตามเงื่อนไข เก็บปัจจัยที่เปลี่ยนกับรายการที่ระบบควรกรองออก ให้กรรมการพิมพ์คำขออื่นได้ด้วย
- [ ] ตรวจเส้นทางที่ใช้ข้อมูลสมมติให้มีป้ายบนรายการและในแชต พร้อมรายการแจ้งกรรมการ ห้ามใช้ผลตอบโมเดลที่แต่งหรือบันทึกไว้ล่วงหน้าเป็นผลสด ข้อห้ามนี้กระทบทั้งคะแนนหมวด 1 และสิทธิ์แข่งขันตาม Booklet หน้า 5–7, 10 และ 17

| งานพัฒนา | จุดเริ่มใน repo | เกณฑ์ตรวจรับ |

## C. ตรวจบนอุปกรณ์และเก็บหลักฐาน

ใช้ APK กับ backend จาก commit เดียวกัน จด device, provider/model, วิธีเชื่อมต่อ และเวลา เก็บ transcript ที่ใช้ข้อมูลทดสอบและปกปิดข้อมูลส่วนบุคคล

| การทดสอบ | สิ่งที่ต้องเห็น | หลักฐาน |
| --- | --- | --- |
| C1. ค้นพบและบันทึก | เริ่มแชตด้วยข้อความสด ได้ `aiStatus: ok` และ `search_opportunities` คืน ID ที่มีข้อมูลต้นทาง เปิดการ์ด ยืนยันบันทึก และตรวจแผนหลังเปิดใหม่ | ผล API ของเทิร์น, IDs และผลยืนยันบันทึก พร้อมวิดีโอ Android |
| C2. เปลี่ยนอินพุต | เปลี่ยนเขตหรือทักษะหนึ่งอย่างแล้วตัวกรองและผลเปลี่ยนตรงเหตุผล ลอง “ดูงานอื่น” และตรวจว่า context คงอยู่ | ตารางอินพุต/ตัวกรอง/IDs ก่อนและหลัง พร้อมผล tool |
| C3. ผลว่างและความล้มเหลว | ทดลองผลว่าง, provider timeout, source เปิดไม่ได้ และ retry หลังการตอบกลับขาดหาย ตรวจว่า UI อธิบายผลและยังทำต่อได้ | ตาราง expected/actual, screenshots และสถานะข้อมูลหลัง retry |
| C4. ซ้อมเสมือนเวที | จับเวลาต่อเนื่อง 10 นาที ใช้เวลานำเสนอ 7 นาที, Q&A 2 นาที, และเวลาเปลี่ยนทีม 1 นาที ไม่มี crash, hang หรือ reload ระหว่างสาธิตและตอบคำถาม | วิดีโอต่อเนื่องหรือบันทึกเวลาของผู้สังเกต พร้อม SHA และผลตรวจเครือข่าย |
| C5. การอ่านและการใช้งาน | ให้ผู้ใช้ใหม่ทำถึงบันทึกแผน อ่านป้ายที่มาและใช้ทางลองใหม่ ตรวจ Android จอเล็กและตัวอักษรขยาย ลองเปิดลิงก์ผ่านเครื่องฉาย | ภาพกับบันทึกจุดที่ผู้ใช้ติด และผลหลังแก้ |

ถ้า C1 ไม่มี tool call, หาไม่พบ, หรือเก็บแผนไม่ได้ ให้บันทึกว่าไม่ผ่านและแก้ที่จุดนั้น เคสผลว่างที่ระบบจัดการได้ใช้เป็นหลักฐาน C3 ได้ ทดสอบ APK ยังรออุปกรณ์ Android หรือ AVD ผล widget test และผล HTTP เดิมรองรับเฉพาะส่วนที่รันจริง

- [ ] ปิดงานพัฒนา B ที่กระทบเส้นหลัก และได้ C1–C3 ที่ตรวจผลได้บน build เดียวกัน จดรายการที่ต้องแก้กลับพร้อมเจ้าของ
- [ ] ใช้ผล C4/C5 และงาน Pitch ปรับสคริปต์เมื่อมีอุปกรณ์ครบ จดว่าหลักฐานใดผ่าน และหลักฐานใดรออุปกรณ์หรือสถานที่
- [ ] เมื่อพฤติกรรมหลักผ่านแล้ว ค่อยปรับ Dev Spec ในข้อ 2 และชุดไฟล์ในข้อ 3 ตามพฤติกรรมที่ยืนยันได้ เก็บเงื่อนไขที่ตรวจได้เฉพาะวันแข่ง เช่น Kiro Log และคำชี้แจงโจทย์ขยาย ไว้ในรายการตรวจวันงาน

ช่วงก่อนแข่งให้เน้นปิดช่องว่างและซ้อมใน repo เตรียมงาน วันแข่งให้ทำตามข้อกำหนด repo ใหม่และการใช้ Kiro ของผู้จัด ใช้ Build วันแข่งสร้างหลักฐานส่งจริงอีกครั้ง [รายละเอียดเวลาส่งและข้อกำหนด](event-runbook.md)
