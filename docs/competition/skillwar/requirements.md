# Requirements สำหรับทางรอดในวันแข่ง

## ผู้ใช้และขอบเขต

ผู้ใช้หลักที่เสนอคือคนกรุงเทพฯ ที่กำลังเปลี่ยนงานหรือมีรายได้ลดลง ต้องการรู้ว่าสิทธิไหนควรตรวจและหางานใกล้บ้านตามเวลาที่ว่าง Persona สำหรับซ้อมเป็นกรณีสมมติ ให้ใช้เขตบางนาเป็นจุดเริ่ม แล้วเปลี่ยนเขตหรือเงื่อนไขต่อหน้ากรรมการ ข้อสังเกตว่าข้อมูลกระจายหลายช่องทางเป็นสมมติฐานสำหรับ pitch ให้หาหลักฐานจริงก่อนอ้างผลกระทบหรือจำนวนคน

ธีมหลักคือ Civic & Public Service Access ผ่านการตรวจสิทธิเบื้องต้นและช่องทางหน่วยงาน ส่วน Urban Living & Environment เชื่อมผ่านการคัดโอกาสหารายได้ตามเขตและเวลาที่มี เส้นหลักบนเวทีเริ่มจากภาษาธรรมชาติและจบที่แผนที่บันทึกได้ คงหน้าโอกาสและ flow ตรวจเองสำหรับผู้ใช้ที่เลือกทำทีละขั้น

## สิ่งที่แอปต้องทำ

| ID | พฤติกรรมที่ผู้ใช้ต้องเห็น | เงื่อนไขผ่าน |
| --- | --- | --- |
| REQ-01 | เปิดทางรอดและเลือกตรวจเอง หรือทดลองเชื่อม ThaID, ทางรัฐ, ประกันสังคม และ D-MyTax แบบจำลอง | เลือกได้ทุกชุดรวมข้ามทั้งหมด เปิดใหม่จำชุดที่เลือก แจ้งที่มาและป้าย DEMO / MOCK |
| REQ-02 | ถามเรื่องสิทธิด้วยคำพูดไทย ระบุข้อเท็จจริงที่ขาดและข้ามได้ | ทราบอายุแล้วไม่ถามซ้ำ คำตอบไม่ทราบไม่กลายเป็นไม่เข้าเกณฑ์ ยอดใช้สูตรหรือข้อมูลที่ตรวจกลับได้ |
| REQ-03 | ขอหางานด้วยภาษาอิสระ ใช้รายละเอียดจากผู้ใช้และคำขอก่อนหน้า | ทดสอบเทิร์นที่เลือกแหล่งข้อมูลจริงหรือ static reference ด้วย model และ search tool ดูผลที่ต่างกันเมื่อเปลี่ยนอินพุต |
| REQ-04 | กรองโอกาสในกรุงเทพฯ และเปิดรายละเอียด ที่มา และข้อมูลติดต่อ | ระบุเขตและหมวดแล้วเห็นรายการตรงเงื่อนไข แผนที่แยกหมุดรวมเขตจากพิกัดจริง ใช้รายการต่อได้หากแผนที่เปิดไม่ได้ |
| REQ-05 | บันทึกโอกาสหรือสิทธิเป็นแผน แล้วทำเครื่องหมายขั้นตอนและเปิดแหล่งติดต่อ | ยืนยันก่อน AI เขียนข้อมูล กดซ้ำได้แผนเดียว เปิดใหม่เห็นขั้นและบริบทเดิม ลิงก์สมัครตัวอย่างติดป้าย |
| REQ-06 | ตั้งเป้ารายได้ด้วยจำนวนและรอบเวลา เห็นที่มาของแต่ละส่วน | ช่วงรวมสัมพันธ์กับ input แยกสิทธิ รายได้ตามประกาศ ประมาณการ และยอดที่ยังต้องตรวจ |
| REQ-07 | ดูโปรไฟล์ บัญชีที่เชื่อม วันที่และที่มาของ facts ตลอดจนแก้ข้อมูลที่กรอกเอง | ค่า false/0 ยังมีความหมาย conflict หรือข้อมูลหมดอายุมีคำถามกลับ การลบหรือสลับ persona คงขอบเขตของแต่ละโปรไฟล์ |
| REQ-08 | ถอน consent ดูสรุปข้อมูลที่เก็บผ่าน export API และลบข้อมูลจากในแอป | แสดงข้อมูล device หลัก ลบรวม Demo scopes และให้สถานะหลังลบกลับสู่ค่าเริ่ม |
| REQ-09 | ยังเดินต่อได้เมื่อ API, model, tiles หรือ source ใช้ไม่ได้ | แสดงข้อผิดพลาดเป็นภาษาไทย มีลองใหม่หรือทางทำต่อ สถานะ fallback ตรงกับที่ใช้จริง |
| REQ-10 | รู้ว่าอะไรเป็นข้อมูลสาธารณะ ตัวอย่าง ค่าคำนวณ หรือข้อมูลแจ้งเอง | ทุกผลที่ใช้ mock มีป้าย เปิด provenance ได้ และเก็บเฉพาะข้อมูลที่ได้รับอนุญาต |
| REQ-11 | ใช้งานบน Android และนำเสนอผ่าน HDMI | ผ่านการซ้อม 7 นาทีพร้อมสไลด์ และคงการทำงานถึงจบช่วง 10 นาที |

## ขอบเขตความเทียบเท่าและวันแข่ง

- **Demo parity** ครอบคลุมพฤติกรรมที่ทำงานจริงใน commit อ้างอิง รวมสถานะผิดพลาดและรูปแบบภาษาไทย ดูเกณฑ์เทียบใน [Dev spec](dev-spec.md)
- **ผลงานแข่งขัน** มี live AI ที่ใช้ผลค้นหาได้จริง เก็บหลักฐานจาก Kiro และตรวจข้อมูลที่ใช้นำเสนอ เมื่อโจทย์ขยายประกาศ ให้บันทึกสิ่งที่เปลี่ยนใน `event-brief.md` พร้อม REQ ที่ได้รับผล
- บริการภาครัฐใน Demo เป็นการจำลองหรือเปิดลิงก์อ้างอิง ผลต่อสิทธิและการรับเข้าทำงานตัดสินที่หน่วยงานหรือนายจ้าง ผู้ใช้บันทึกผลด้วยตัวเอง
- ความแม่นของแชต “ใกล้บ้าน” ระดับเขตเป็นช่องว่างของต้นแบบ ปิดด้วยตัวกรองเขตแบบระบุชัดบน backend และทดสอบผลจากทั้งคำขอแรกกับคำต่อเนื่องก่อนอ้างบนเวที

## ตรวจรับก่อนนับว่าเทียบเท่า

ใช้ [กรณีทดสอบ](qa-scenarios.json) และชุดทดสอบที่ Dev spec อ้างอิง เก็บ SHA, เวอร์ชันเครื่องมือ, ผลทดสอบ, ภาพ Android ของหน้าหลัก, และผล API ก่อนกับหลังบันทึก สำหรับไอดีหรือวันที่ซึ่งระบบสร้างระหว่างรัน ให้เทียบความสัมพันธ์และรูปแบบ ผลจากโมเดลให้เทียบเจตนา รายการที่อ้างอิงได้ และการกระทำที่ตามมา
