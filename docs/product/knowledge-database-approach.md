# แนวทางการสร้างฐานข้อมูลของโครงการ Money Anywhere

**สถานะ:** บันทึกแนวทางและข้อวิเคราะห์จากการหารือ เป็นข้อเสนอ ยังไม่ใช่การตัดสินใจ และไม่ใช่เอกสารขั้นตอนของ AI-DLC
**เอกสารที่เกี่ยวข้อง:** [requirements.md](requirements.md), [thailand-job-data-sources.md](thailand-job-data-sources.md)
**หมายเหตุ:** ข้อสรุปในไฟล์นี้เขียนจากความรู้ทั่วไปและผลการค้นหาที่บันทึกไว้ในไฟล์แหล่งข้อมูล ยังไม่ได้อ่านข้อกำหนดการใช้งานของแหล่งข้อมูลใด และยังไม่ได้เลือกเทคโนโลยี (ตามส่วนที่ 7 ของ requirements ต้องตัดสินใจในขั้นออกแบบของ AI-DLC)

## 1. ข้อเสนอ

สร้างฐานข้อมูลเก็บข้อมูลเอง สร้าง API ของตัวเองให้แอปมือถือเรียกใช้ และมีโปรเซสไปหาข้อมูลจากแหล่งต่างๆ มาอัปเดตแบบ incremental (อัปเดตเฉพาะรายการที่เปลี่ยน)

**ข้อสรุปจากการวิเคราะห์:** ทิศทางถูกต้อง และตรงกับ requirements ที่ต้องการแหล่งที่มาตรวจสอบได้ แต่เหมาะกับข้อมูลบางประเภทเท่านั้น และมีความเสี่ยงเรื่องสิทธิ์ในการเก็บข้อมูล

## 2. ข้อดี

| ข้อดี | รายละเอียด |
|---|---|
| ควบคุมคุณภาพได้ | ทุกรายการมีแหล่งที่มา วันที่ตรวจ และสถานะ ตรงกับ FR-03 และ FR-08 |
| แอปเร็วและเสถียร | แอปเรียกฐานข้อมูลของเรา ไม่ต้องรอหรือพึ่งเว็บต้นทางทุกครั้ง |
| ไม่ผูกกับแหล่งเดียว | ถ้าแหล่งหนึ่งล่ม ข้อมูลเดิมยังแสดงได้ (พร้อมบอกว่าเก่า) |
| ลดต้นทุน API | แหล่งที่จำกัดโควตา เช่น JSearch ฟรีประมาณ 200 คำขอต่อเดือน ไม่ต้องเรียกซ้ำทุกครั้ง |
| ทดสอบได้ | ข้อมูลอยู่ในที่เดียว ทำชุดทดสอบและผูกหลักฐานกับ commit ได้ (AC-05) |
| Incremental ประหยัด | เขียนเฉพาะรายการที่เปลี่ยน และเห็นประวัติการเปลี่ยนแปลงชัด |

## 3. ข้อเสียและความเสี่ยง พร้อมวิธีแก้

| # | ข้อเสีย / ความเสี่ยง | ทางแก้ | ผลที่ยังเหลืออยู่ |
|---|---|---|---|
| 1 | **สิทธิ์ในการเก็บและแสดงซ้ำ** ข้อกำหนดของบางแหล่งห้ามเก็บระยะยาวหรือแสดงซ้ำ เป็นความเสี่ยงสำคัญที่สุด | ทำทะเบียนแหล่งข้อมูล (source register) บันทึกว่าแต่ละแหล่งเก็บได้ แสดงซ้ำได้ ใช้เชิงพาณิชย์ได้ไหม พร้อมลิงก์ข้อกำหนด ใช้เฉพาะแหล่งที่ผ่านการตรวจ เก็บเท่าที่จำเป็น (ชื่อ ลิงก์ วันที่) และลิงก์กลับต้นทาง ถ้าไม่ชัดเจนให้ถามเจ้าของแหล่งเป็นลายลักษณ์อักษร | ต้องมีคนอ่านข้อกำหนดทีละแหล่ง และข้อกำหนดอาจเปลี่ยน |
| 2 | **ตำแหน่งงานเก่าเร็ว** | ไม่เก็บถาวร ใช้แคชอายุสั้น (1 ชั่วโมงถึง 1 วัน) แอปแสดง "ข้อมูล ณ เวลา..." และปุ่มเปิดหน้าต้นทาง ถ้าแคชหมดอายุและต้นทางเรียกไม่ได้ ให้แจ้งว่าไม่มีข้อมูลสด | ผู้ใช้อาจเห็นงานที่เพิ่งปิดในช่วงอายุแคช |
| 3 | **แหล่งที่ไม่มี API ต้องใช้คน** | เริ่มจาก 10–20 รายการต่อหมวด จัดลำดับตามความเสี่ยง (ทุนที่มีวันปิดรับตรวจบ่อยกว่ากฎที่เปลี่ยนช้า) ใช้เช็กลิสต์ตรวจมาตรฐาน งานอัตโนมัติช่วยตรวจลิงก์และเทียบแฮชหน้าเว็บเพื่อบอกว่า "หน้าต้นทางเปลี่ยน ควรตรวจ" | ยังพึ่งคน ไม่มีทางอัตโนมัติเต็มรูปแบบ |
| 4 | **ภาระงานดูแลต่อเนื่อง** ทีมมี 3 คน | แบ่งผู้รับผิดชอบรายหมวด เขียนคู่มือตรวจสั้นๆ ตั้งแจ้งเตือนเมื่องานดึงข้อมูลล้มเหลวหรือรายการเก่าเกินรอบ ถามเจ้าของโครงการเรื่องผู้ดูแลหลังการแข่งขัน | ต้องตัดสินเรื่องงบและคนก่อนใช้จริง |
| 5 | **Incremental ตรวจยาก** ต้นทางมักไม่บอกว่ารายการไหนเปลี่ยน | ใช้ `source_url` เป็นคีย์ เก็บแฮชเนื้อหา เมื่อแฮชเปลี่ยนให้ส่งเข้าคิวตรวจ ไม่เขียนทับอัตโนมัติ รายการที่หายไปให้ตั้งสถานะ "ต้องตรวจ" แทนการลบ เก็บประวัติเวอร์ชัน และเขียนชุดทดสอบกรณีเพิ่ม แก้ ลบ ไม่เปลี่ยน | แฮชเปลี่ยนจากสาเหตุไม่สำคัญ (เช่นโฆษณา) ทำให้แจ้งเตือนเกินจริง ต้องจูนส่วนของหน้าที่เทียบ |
| 6 | **ซับซ้อนเกินสโคป MVP** | ทำเป็น 3 ระยะ (ดูส่วนที่ 6) ตัดสินใจไประยะถัดไปเมื่อข้อมูลหรือผู้ใช้โตจนจำเป็น | MVP ไม่ใช่ระบบเต็มรูปแบบ |

### ความเสี่ยงเพิ่มเติม

| ความเสี่ยง | ทางแก้ |
|---|---|
| AI สรุปผิดหรือแต่งข้อมูล | ให้ AI อ้างอิงเฉพาะรายการในฐานข้อมูล ทุกคำตอบชี้กลับไปที่รายการและแหล่งที่มา ห้ามเผยแพร่ข้อความสรุปโดยไม่ผ่านคนตรวจ และมีชุดทดสอบกรณีที่ AI ควรตอบว่า "ไม่ทราบ" |
| แหล่งต้นทางเปลี่ยนรูปแบบหรือปิดตัว | ตรวจลิงก์ทุกสัปดาห์ และมีแหล่งสำรองสำหรับเรื่องเดียวกันถ้าเป็นไปได้ |
| ข้อมูลส่วนบุคคลของผู้ใช้รั่ว | เก็บให้น้อยที่สุด ไม่ฝัง API key ในแอป แยกฐานข้อมูลผู้ใช้ออกจากฐานความรู้ ใช้โปรไฟล์สมมติตอนสาธิต |
| ข้อมูลสองแหล่งขัดแย้งกัน | กำหนดลำดับความน่าเชื่อถือ (หน่วยงานเจ้าของเรื่องมาก่อน) ตั้งสถานะ "ขัดแย้ง" และแจ้งผู้ใช้ ตาม FR-08 |
| ผู้ใช้เข้าใจว่าเป็นการรับรองสิทธิ์ | ใส่ข้อความ "ไม่รับประกันสิทธิ์" ทุกหน้าที่เกี่ยวข้อง และปุ่มไปช่องทางทางการเพื่อยืนยัน |

## 4. ประเภทข้อมูลไหนควรเก็บเอง

| ประเภท | เก็บในฐานข้อมูลเองเหมาะไหม | เหตุผล |
|---|---|---|
| กฎ สวัสดิการ ทุน (หมวด 1, 2, 3, 9) | **เหมาะที่สุด** | ข้อมูลเปลี่ยนช้า ไม่มี API ให้เรียกสด และคนคัดมีคุณค่า |
| สถิติจากข้อมูลเปิด | เหมาะ | เผยแพร่เป็นรอบ เก็บแล้วอ้างอิงได้ ต้องตรวจสัญญาอนุญาตก่อน |
| ตำแหน่งงาน (หมวด 4, 5, 6) | **ไม่เหมาะ ควรแคชสั้น** | เก่าเร็ว และมีข้อจำกัดเรื่องการเก็บ เรียกต้นทางตอนผู้ใช้ขอ |
| ประมาณการและไอเดียรายได้ (หมวด 7, 8, 10) | เก็บเฉพาะสมมติฐาน | ให้ AI คำนวณตอนใช้งานจากสมมติฐานที่เก็บไว้ ระบุว่าเป็นประมาณการ |

## 5. แนวทางการออกแบบ

### 5.1 สองชั้นข้อมูล

1. **ชั้นความรู้ (เก็บถาวร มีเวอร์ชัน):** กฎ สวัสดิการ ทุน อัปเดตด้วยคน และให้งานอัตโนมัติตรวจลิงก์
2. **ชั้นแคชสด (อายุสั้น):** ตำแหน่งงานจาก API ทางการ อัปเดตตามคำขอ

### 5.2 โครงสร้างโดยรวม

```
แหล่งข้อมูลที่ได้รับอนุญาต
   │
   ▼
[งานตั้งเวลา: ดึงข้อมูล + ตรวจลิงก์]
   │   ┌── ข้อมูลที่คนต้องตรวจ ──► [คิวตรวจโดยคน] ──┐
   ▼   ▼                                             ▼
        [ฐานข้อมูลของเรา + ประวัติเวอร์ชัน]
                     │
                     ▼
              [API ของเรา] ──► [แอปมือถือ]
```

### 5.3 ฟิลด์ที่เสนอให้มีในแต่ละรายการ (ต้องตัดสินในขั้นออกแบบของ AI-DLC)

- `id`, `category` (หมวดที่ 1 ถึง 10)
- `title`, `summary`, `conditions`
- `source_url`, `source_owner`
- `last_verified` (วันที่ตรวจล่าสุด), `verified_by`
- `valid_until` หรือ `deadline`
- `status`: ปัจจุบัน, เก่า, หมดอายุ, ขัดแย้ง หรือต้องตรวจ
- `content_hash` (ใช้เทียบเพื่อทำ incremental)
- `version`
- `data_label`: ข้อเท็จจริงมีแหล่งที่มา, AI คาดเดา, ผู้ใช้บอกเอง, ประมาณการ, ไม่ทราบ หรือ DEMO / MOCK (ตามส่วนที่ 6 ของ requirements)

### 5.4 ทะเบียนแหล่งข้อมูล (source register)

ใช้ตรวจก่อนนำแหล่งใดเข้าระบบ

| ฟิลด์ | ความหมาย |
|---|---|
| `source_name`, `owner` | ชื่อและเจ้าของแหล่ง |
| `terms_url` | ลิงก์ข้อกำหนดการใช้งาน |
| `can_store` | เก็บข้อมูลได้ไหม และนานเท่าใด |
| `can_redisplay` | แสดงซ้ำต่อผู้ใช้ได้ไหม |
| `commercial_use` | ใช้เชิงพาณิชย์ได้ไหม |
| `access_method` | API ทางการ, ข้อมูลเปิด, หน้าเว็บอ้างอิง หรือขออนุญาตแล้ว |
| `checked_by`, `checked_on` | ผู้ตรวจและวันที่ตรวจเงื่อนไข |
| `approved` | อนุมัติให้ใช้หรือไม่ |

### 5.5 ขั้นตอนอัปเดตแบบ incremental

1. ดึงข้อมูลจากแหล่งที่ `approved` ตามรอบของประเภทข้อมูล
2. คำนวณ `content_hash` ของส่วนที่ใช้เทียบ (ตัดส่วนที่ไม่สำคัญ เช่นโฆษณา)
3. เทียบกับค่าที่เก็บไว้
   - ไม่เปลี่ยน: ไม่ทำอะไร
   - เปลี่ยน: ส่งเข้าคิวตรวจโดยคน ไม่เขียนทับอัตโนมัติ
   - รายการใหม่: ส่งเข้าคิวตรวจ
   - รายการหายไป: ตั้งสถานะ "ต้องตรวจ" ไม่ลบทันที
4. คนยืนยันกับหน้าต้นทาง แล้วอัปเดตเนื้อหา `last_verified` และ `version`
5. รายการที่เลย `deadline` ให้ซ่อนอัตโนมัติ
6. บันทึกประวัติเวอร์ชัน ผูกกับ commit หรือ log ที่ย้อนดูได้

### 5.6 รอบการอัปเดตที่เสนอ

| ประเภทข้อมูล | ตัวอย่าง | รอบ | วิธีทำ |
|---|---|---|---|
| กฎและเงื่อนไข | เงื่อนไขสวัสดิการ ขั้นตอนขอคืนภาษี | ทุก 3 เดือน และเมื่อมีประกาศเปลี่ยน | คนตรวจหน้าต้นทาง แล้วอัปเดต `last_verified` |
| ข้อมูลมีกำหนดเวลา | ทุนที่มีวันปิดรับ | ทุกสัปดาห์ และหมดอายุอัตโนมัติ | ใช้ `deadline` ซ่อนเมื่อเลยกำหนด |
| รายการสดจาก API | ตำแหน่งงาน | ตอนผู้ใช้ขอ แคช 1 ชั่วโมงถึง 1 วัน | เรียก API เมื่อต้องใช้ ไม่เก็บระยะยาว |
| สถิติ | ค่าจ้าง อัตราว่างงาน | ตามรอบที่แหล่งเผยแพร่ | ดึงแล้วบันทึกวันที่เผยแพร่ |
| ประมาณการ | ไอเดียรายได้ สมมติฐานต้นทุน | เมื่อสมมติฐานเปลี่ยน | ทบทวนกับเจ้าของโครงการ ระบุว่าเป็นประมาณการ |

### 5.7 ฝั่งแอปมือถือและ API

- แอปเรียกเฉพาะ API ของเรา ไม่เรียกแหล่งต้นทางตรง และไม่ฝัง API key ในแอป
- API ส่ง `last_verified` และ `status` ไปพร้อมข้อมูล แอปแสดง "ตรวจล่าสุดเมื่อ..." และเตือนเมื่อข้อมูลเก่า (FR-08)
- แอปแคชในเครื่องได้ แต่ต้องเก็บ `last_verified` ไปด้วย และรีเฟรชเมื่อเปิดแอปหรือเมื่อข้อมูลเกินอายุ
- ถ้า API ล่มหรือไม่มีผลลัพธ์ ให้แจ้งตรงๆ ห้ามแสดงข้อมูลเก่าโดยไม่บอก

## 6. ลำดับการทำ (3 ระยะ)

| ระยะ | สิ่งที่ทำ | เงื่อนไขไประยะถัดไป |
|---|---|---|
| 1 (MVP) | ไฟล์ JSON ที่คัดเองใน repository สำหรับสาย A (10–20 รายการต่อหมวด) พร้อมสคริปต์ตรวจลิงก์ และทะเบียนแหล่งข้อมูล | MVP ผ่านเกณฑ์ AC-01 ถึง AC-05 |
| 2 | ย้ายเข้าฐานข้อมูลและ API ของเราเอง พร้อมแคชสั้นสำหรับตำแหน่งงานผ่าน API ที่ตรวจเงื่อนไขแล้ว | ข้อมูลหรือผู้ใช้โตจน JSON จัดการไม่ไหว |
| 3 | งานดึงข้อมูลอัตโนมัติแบบ incremental พร้อมคิวตรวจโดยคนและการแจ้งเตือน | มีผู้ดูแลและงบประมาณที่ตกลงแล้ว |

ขั้นตอนเริ่มต้นแนะนำ:
1. ทำทะเบียนแหล่งข้อมูลและตรวจเงื่อนไขการใช้ (ความเสี่ยงที่ 1 ก่อน เพราะกระทบทุกอย่าง)
2. สร้างชุดข้อมูลสาย A แบบ JSON พร้อมฟิลด์ตามส่วนที่ 5.3
3. เขียนสคริปต์ตรวจลิงก์และเทียบแฮช ส่งผลเข้าคิวตรวจ
4. ใช้แคชสั้นกับตำแหน่งงาน เมื่อตรวจเงื่อนไข API แล้ว
5. เมื่อ MVP เสถียร ค่อยพิจารณาฐานข้อมูลและโปรเซสเต็มรูปแบบ

## 7. ตัววัดผล

- จำนวนรายการที่เก่าเกินรอบอัปเดต
- จำนวนลิงก์เสีย
- จำนวนงานดึงข้อมูลที่ล้มเหลว
- สัดส่วนรายการที่มี `source_url` และ `last_verified` ครบ
- จำนวนคำตอบของ AI ที่ไม่มีแหล่งอ้างอิง (ควรเป็น 0)

## 8. คำถามที่ต้องตัดสิน

- ข้อกำหนดของแต่ละแหล่งอนุญาตให้เก็บและแสดงซ้ำหรือไม่
- ใครดูแลโปรเซสและการตรวจโดยคนหลังจบการแข่งขัน (เป็นเรื่องค่าใช้จ่ายและขอบเขต ต้องถามเจ้าของโครงการ)
- ใช้ฐานข้อมูลและเทคโนโลยีใด (ตัดสินในขั้นออกแบบของ AI-DLC)
- กฎหมายข้อมูลส่วนบุคคลและลิขสิทธิ์ที่เกี่ยวข้อง ควรปรึกษาผู้เชี่ยวชาญก่อนเปิดใช้จริง
