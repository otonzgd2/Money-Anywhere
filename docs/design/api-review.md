# API Review

## v0.3 (เพิ่มตามหน้าบ้าน: เงินอยู่ไหน, PDPA, ThaID ซ่อน, ผู้ช่วย AI)
- **PDPA:** `GET /v1/privacy/notice`, `GET/POST /v1/me/consents` แยกวัตถุประสงค์ core/location/ai/reminders/gov มีเลขฉบับ ยืนยันอายุ ถอนมีผลทันที server ตอบ 403 `CONSENT_REQUIRED` เมื่อจะบันทึกโดยไม่ได้ยินยอม AI ไม่ยินยอมใช้กฎและตอบ `skipped_no_consent`
- **รวมที่ซ้ำ:** `settings.reminders` ซ้ำกับความยินยอมข้อ reminders ตัดออก เหลือที่ความยินยอมที่เดียว
- **เงินอยู่ไหน:** `GET /v1/money`, `GET/PATCH /v1/money/{id}`, `GET/PATCH /v1/me/facts` กฎเป็นข้อมูลใน `moneyPrograms` มีเวอร์ชัน
- **เริ่มรับเงินใช้เส้นเดิม:** `POST /v1/tasks` รับ `moneyId` ได้ ไม่สร้าง endpoint ใหม่
- **ผลลัพธ์:** event `report_outcome` บน `/v1/tasks/{id}/events` เดิม
- **ThaID:** `/v1/me/gov-link`, `/callback` หลัง feature flag ปิดแล้วตอบ 404 `FEATURE_DISABLED`
- **ผู้ช่วย AI:** `/v1/ai/conversations*` เครื่องมืออ่านทำทันที เครื่องมือเขียนต้องยืนยัน, `/v1/me/memory*`
- **อื่นๆ:** `GET /v1/health` (commit), `GET /v1/plans/ideas`, `suggestions` เมื่อไม่พบผล, `POST /v1/demo/personas/{id}`, explanation รับ `subjectType: money`
- **แยกไว้ตั้งใจ:** facts แยกจาก profile เพราะ profile ใช้จับคู่โอกาส ส่วน facts ใช้ตรวจสิทธิ์และเป็นข้อมูลที่อ่อนไหวกว่า ถามทีละข้อ ลบทีละข้อได้

## v0.1 → v0.2

ตรวจทานสัญญา API ทั้งชุด ตอบ 4 คำถาม: ถูกต้องไหม, ตามมาตรฐานไหม, มีเส้นซ้ำไหม, รองรับระบบภายนอกไหม
ผลทดสอบหลังแก้: `npm test` ใน `contracts/` ผ่านทั้งหมด (OpenAPI 3.0.3 valid, config ตรง schema, 27/27 operations ถูกเรียกจริง)

## 1. สิ่งที่ผิดหรือขาดใน v0.1 และแก้แล้ว
| # | ปัญหา | ผลกระทบ | แก้เป็น |
|---|---|---|---|
| 1 | ไม่มีตัวระบุผู้ใช้ mock เก็บข้อมูลรวมทุกคน | 3 คนทดสอบพร้อมกันแล้วเห็นงานของกันและกัน | ทุก request จากแอปส่ง `X-Device-Id` แยกข้อมูลรายเครื่อง (ทดสอบแล้วว่าแยกจริง) |
| 2 | `DELETE /v1/me/profile` ลบทั้งงานและการตั้งค่าด้วย | ชื่อไม่ตรงกับสิ่งที่ทำ | `DELETE /v1/me` ลบทุกอย่าง, profile ไม่มี DELETE แยก |
| 3 | งานมี 5 เส้นที่เป็นคำกริยา (`/steps/complete`, `/undo`, `/block`, `/snooze`, `/help`) | เพิ่มการกระทำใหม่ต้องเพิ่ม endpoint ทุกครั้ง, undo ไม่มีประวัติให้อ้าง | รวมเป็น `POST /v1/tasks/{id}/events` ที่มี `type` และ `GET` ดูประวัติ ส่วน help ย้ายไป AI |
| 4 | กดซ้ำสองครั้งทำขั้นข้ามไป 2 ขั้น | ผู้สูงอายุมักแตะซ้ำ | `Idempotency-Key` บน event (ทดสอบแล้วว่ากดซ้ำมีผลครั้งเดียว) |
| 5 | เอางานออกจากแผนไม่ได้ | ฟีเจอร์ขาด | `DELETE /v1/tasks/{id}` |
| 6 | ตำแหน่งซ้ำสองที่: `profile.lat/lng` กับ `settings.searchPoint` | ข้อมูลขัดกันได้ | เหลือที่ profile, จุดค้นหาชั่วคราวส่งเป็น query `lat/lng` |
| 7 | `OpportunityPage.sources` ส่งสถานะแหล่งข้อมูลทั้งหมดซ้ำทุกครั้งที่ค้นหา | ข้อมูลซ้ำกับ `/v1/sources` และหนักเปล่า | เหลือ `sourceWarnings` (รายชื่อเจ้าที่ล้ม) |
| 8 | ตัวกรองหมวดพิมพ์ชื่อหมวดซ้ำกับ taxonomy | แก้ชื่อหมวดต้องแก้สองที่ | `optionsFrom: mapGroups` อ่านจาก taxonomy |
| 9 | chat ใช้ sessionId ที่แอปสร้างเอง | ชนกันได้, ไม่มีที่ให้เริ่มใหม่ | `POST /v1/intake/sessions` แล้ว `POST .../{id}/messages` |
| 10 | บาง endpoint คืน 404/422 ที่ไม่ได้ประกาศ | แอปไม่รู้ว่าต้องรับมือ | ประกาศครบ test ตรวจว่าไม่มี status ที่ไม่ได้ประกาศ |
| 11 | รายการบางที่เป็น array ตรงๆ บางที่ห่อ object | ไม่สม่ำเสมอ เพิ่ม metadata ไม่ได้ | ทุกรายการห่อเป็น `{items}` |
| 12 | Error ไม่มี status และ requestId | ตามหาปัญหายาก | Error มี `status`, `requestId` ตรงกับ header `X-Request-Id` |
| 13 | ความยินยอมเขียนทับ ไม่มีประวัติ | ตรวจย้อนไม่ได้ว่ายอมรับเวอร์ชันไหน | `POST /v1/me/consents` เก็บทุกเวอร์ชัน ส่งออกได้ |
| 14 | ส่งออกข้อมูลไม่ครบ (ไม่มีงาน การตั้งค่า ความยินยอม) | ไม่ตรงกับหน้า ข้อมูลของฉัน | `GET /v1/me/export` คืนครบ |

## 2. เส้นไหนรวม เส้นไหนแยก
หลัก: รวมเมื่อเป็น resource เดียวกันและต่างกันแค่ค่าข้อมูล แยกเมื่อหน้าที่ต่างกันหรือจะโตไปคนละทาง

| กลุ่ม | ตัดสินใจ | เหตุผล |
|---|---|---|
| ทำขั้นเสร็จ / เลิกทำ / ติดปัญหา / เลื่อน / กลับมาทำต่อ | **รวม** เป็น `POST /tasks/{id}/events` | เป็นการเปลี่ยนสถานะของงานเดียวกัน ต่างแค่ `type` เพิ่มชนิดใหม่ (เช่น `external_verified`) ไม่ต้องเพิ่ม endpoint |
| AI อธิบายขั้นตอน / อธิบายเงื่อนไขโอกาส | **รวม** เป็น `POST /ai/explanations` | ใช้ adapter และกติกาเดียวกัน ต่างแค่ `subjectType` |
| AI จัดอันดับ กับ AI อธิบาย | **แยก** | input/output คนละแบบ (รายการ id กับข้อความ) และจะปรับ model/ค่าใช้จ่ายแยกกัน แต่ใช้ adapter AI ตัวเดียว |
| ทำขั้นเสร็จ (เดิม `/steps/complete`) กับ PATCH task | **ไม่ใช้ PATCH** | แอปต้องไม่ตั้ง `doneCount` เอง server ต้องคุมลำดับและ undo จึงใช้ event |
| profile กับ settings | **แยก** | profile ใช้จับคู่โอกาส (เปลี่ยนแล้วต้องค้นใหม่) settings เป็นการแสดงผล เปลี่ยนแล้วไม่กระทบผลค้นหา |
| export กับ profile | **แยก** | export รวมทุกอย่างเพื่อสิทธิ์ของเจ้าของข้อมูล profile ใช้งานประจำ |
| ค้นหา กับ ดูรายการเดียว | **แยก** | รายการเดียวต้องเปิดได้จากลิงก์โดยไม่ต้องค้นใหม่ |
| ค้นหาแบบรายการ กับ แผนที่ | **รวม** `GET /opportunities` | ข้อมูลชุดเดียว ต่างแค่วิธีแสดงในแอป |
| ค้นหา กับ จัดอันดับ AI | **แยก** | ค้นหาต้องเร็วและแน่นอน AI ช้ากว่าและล้มได้ แยกแล้วแอปแสดงผลค้นหาก่อน แล้วเติมเหตุผล AI ทีหลัง |
| แผนรายได้ กับ โอกาส | **แยก** | แผนมีสมมติฐานและการคำนวณของตัวเอง บางแผนไม่ผูกกับโอกาสใดเลย |
| ส่งข้อมูลเข้าเป็นชุด กับ webhook | **แยก** | ชุด = ทีม curate อัปโหลดทั้งก้อน, webhook = แจ้งเหตุทีละรายการ อัตราและการลองใหม่ต่างกัน |
| ดึงจากแหล่ง (pull) กับ ส่งเข้า (push) | **ใช้ฟิลด์กลางเดียวกัน** (`OpportunityInput`) | เพิ่มแหล่งใหม่ไม่ว่าทางไหน ผลลัพธ์เหมือนกัน |

ฝั่งแอปยังมี action id แยกตามความหมาย (`task.step.complete`, `task.snooze` ฯลฯ) แต่หลายตัวชี้ endpoint เดียวกันพร้อม `body` คงที่ หน้าจอจึงอ่านง่าย ส่วน API ไม่ซ้ำ

## 3. มาตรฐานที่ใช้
ใช้แนวปฏิบัติ REST ทั่วไปที่มาตรฐานส่วนใหญ่มีตรงกัน: path เป็นคำนามพหูพจน์, รุ่นใน path, status code ตามความหมาย, error รูปแบบเดียว, แบ่งหน้า, idempotency, request id, ETag, PATCH แบบ merge ตารางเต็มอยู่ในหน้า HTML หัวข้อ "มาตรฐานที่ใช้"

**ยังไม่ได้ยืนยัน "TM standard":** ถ้าหมายถึง TM Forum (TMF630 REST API Design Guidelines) ส่วนที่ยังไม่ตรงและต้องตัดสินก่อนแก้มีดังนี้ ผมยังไม่ได้เปิดเอกสาร TMF630 ฉบับล่าสุดเทียบทีละข้อ รายการนี้มาจากความรู้ทั่วไป
| เรื่อง | TMF630 (โดยทั่วไป) | ตอนนี้ |
|---|---|---|
| ฟิลด์ประจำ resource | `id`, `href`, `@type`, `@baseType`, `@schemaLocation` | มีแค่ `id` |
| รายการ | array ตรงๆ + header `X-Total-Count`, `X-Result-Count` | `{items}` + `X-Total-Count` |
| แบ่งหน้า | `offset` + `limit` | `cursor` + `limit` |
| เลือกฟิลด์ | `fields=` | ไม่มี |
| Error | `code`, `reason`, `message`, `status`, `referenceError`, `@type` | `code`, `message`, `status`, `retryable`, `requestId` |
| PATCH | `application/merge-patch+json` | merge แบบ JSON ธรรมดา |
| แจ้งเหตุ | hub/listener (`/hub`, `/listener/...Event`) | webhook ต่อผู้ให้ข้อมูล |
ถ้าเป็นมาตรฐานภายในองค์กรอื่น ส่งเอกสารมาแล้วผมเทียบให้

## 4. การเชื่อมต่อภายนอก
แต่ละบริการภายนอกเป็น port ที่มี interface เดียว เปลี่ยนผู้ให้บริการได้โดยไม่แก้ API หรือแอป รายละเอียดใน `contracts/integrations.json`

| port | ทิศทาง | สถานะ |
|---|---|---|
| AI provider | ออก | rules ใช้ได้, OpenAI-compatible ใช้ได้และทดสอบกับ LLM จำลองแล้ว (ตัด id ที่แต่ง, ตัดตัวเงิน, ล้มแล้ว fallback) ยังไม่ทดสอบกับผู้ให้บริการจริง |
| แหล่งโอกาส (ดึง) | ออก | Greenhouse, Lever ใช้ได้และดึงจริงแล้ว; data.go.th, OSM วางแผน |
| แหล่งโอกาส (ส่งเข้า) | เข้า | batch upsert + webhook ใช้ได้ ตรวจ `X-Api-Key` |
| หาพิกัด | ออก | ตารางเขต ใช้ได้; Nominatim วางแผน |
| แจ้งเตือน | ออก | memory ใช้ได้; FCM วางแผน |
| แผนที่ | ออก (แอปเรียกตรง) | วางแผน |
| ส่งต่อช่องทางทางการ | ออก | ลิงก์ออกเท่านั้น |

ไม่ได้ทำตาม requirements ข้อ Deferred: ฐานข้อมูลสิทธิ์ของรัฐรายบุคคล, ยื่นแทนผู้ใช้, โอนเงิน ส่วนสถานะยืนยันจากภายนอก (`reportedBy: external`) เตรียมช่องไว้ใน Task แต่ยังไม่เปิดใช้
