# ทางเลือกเรื่องข้อมูลรัฐ และ PDPA

สถานะ: ข้อเสนอ รอ Owner ตัดสิน ข้อนี้แตะ requirements ข้อ 9 (Deferred: identity verification และการเชื่อมฐานข้อมูลสิทธิ์รายบุคคลของรัฐ)
รายการบริการรัฐเรื่องเงิน, แอปที่ต้องเชื่อม และข้อมูลแผนที่: `docs/design/gov-services-inventory.md`

## 1. โจทย์
- ถ้าเชื่อมระบบรัฐได้ (ThaID, ข้อมูลสิทธิ์รายบุคคล): แอปบอกได้ว่า "คุณมีเงินรอรับ X บาท" มีค่ามาก
- ถ้าเชื่อมไม่ได้: เสี่ยงกลายเป็นแอปรวมลิงก์ ซึ่ง requirements ข้อ 5 บอกว่าห้ามเป็นแค่นั้น

## 2. ข้อเท็จจริงที่ต้องรู้
- ThaID เป็นแอปยืนยันตัวตนของกรมการปกครอง ([Google Play](https://play.google.com/store/apps/details?id=th.go.dopa.bora.dims.ddopa)) การให้ระบบอื่นใช้ ThaID ล็อกอินต้องผ่านการตกลงกับหน่วยงานเจ้าของ ไม่มีช่องทางให้นักพัฒนาทั่วไปสมัครใช้เองที่ผมยืนยันได้
- NDID เป็นเครือข่ายยืนยันตัวตนแบบสมาชิก ธนาคารหรือสมาชิกที่ยืนยันตัวตนแล้วยืนยันต่อให้ธุรกิจอื่นโดยผู้ใช้ยินยอม เอกชนเป็นสมาชิกได้แต่ต้องสมัครเข้าเครือข่าย ([สรุปจาก didit.me](https://didit.me/blog/ndid-thailand/))
- ข้อมูลรายบุคคลของรัฐผ่าน GDX ต้องได้รับอนุญาตจากหน่วยงานเจ้าของข้อมูล (บันทึกไว้ใน handoff Money Map)
- สรุป: เชื่อมระบบรัฐจริงทำได้ แต่ต้องมีข้อตกลง, DPIA และงานความปลอดภัย ไม่ทันช่วงแข่งและขัดกับกฎ Demo ใน `project.md`

ผมยังไม่ได้ตรวจเงื่อนไขล่าสุดของ ThaID และ NDID จากเอกสารของหน่วยงานโดยตรง ต้องตรวจก่อนตัดสินใจทำเวอร์ชันเชื่อมต่อ

## 3. ทำให้มีประโยชน์ได้โดยไม่ต้องเชื่อมระบบรัฐ
คุณค่าจริงไม่ได้อยู่ที่ตัวเลขเงินอย่างเดียว คนส่วนมากไม่รู้ว่าตัวเองควรเช็คสิทธิ์อะไร ไม่รู้ว่าเช็คที่ไหน และทำไม่จบ

| ความสามารถ | ทำอย่างไรโดยไม่ใช้ API รัฐ | ต่างจากแอปรวมลิงก์อย่างไร |
|---|---|---|
| ตรวจสิทธิ์เบื้องต้น | กฎจากเกณฑ์ที่ประกาศสาธารณะ (อายุ รายได้ สถานะงาน) มีเวอร์ชัน ตอบ "น่าจะมีสิทธิ์ / น่าจะไม่มี / ข้อมูลไม่พอ" พร้อมเหตุผล | บอกว่าควรเช็คอะไร ก่อนเปิดลิงก์ |
| ประมาณจำนวนเงินจากอัตราที่ประกาศ | เช่น อัตราเบี้ยยังชีพตามช่วงอายุ ติดป้าย "อัตราตามประกาศ ยังไม่ยืนยันสิทธิ์ของคุณ" | เห็นมูลค่าที่อาจได้ |
| พาไปเช็คแบบมีขั้นตอน | เปิดหน้าทางการพร้อมบอกว่าต้องกดอะไร ต้องเตรียมเอกสารอะไร | ทำจบได้จริง |
| ถามผลเมื่อกลับมา | "เช็คแล้วได้ผลอย่างไร" ผู้ใช้กรอก บันทึกเป็นผู้ใช้แจ้ง | มีความคืบหน้าและผลลัพธ์ |
| เตือนรอบสมัครและกำหนดส่ง | ปฏิทินรอบจากประกาศ | ไม่พลาดรอบ |
| รวมงานจริงจาก API เอกชน | Greenhouse, Lever (ใช้ได้แล้ว) + ข้อมูลคัดมือ | ได้งานจริง |
| วางแผนรายได้ | คำนวณตรงจากค่าจ้างและเวลาว่าง | ตัดสินใจได้ |
| เตือนมิจฉาชีพ | กฎ + รายงาน | ปลอดภัยขึ้น |

## 4. ข้อเสนอ: แอปเดียว สองโหมด
| | โหมด 1 "ผู้ช่วยนำทาง" (ทำตอนนี้) | โหมด 2 "เชื่อมระบบรัฐ" (อนาคต) |
|---|---|---|
| ยืนยันตัวตน | ไม่มี ใช้ device id | ThaID หรือ NDID |
| ข้อมูลสิทธิ์ | กฎจากเกณฑ์สาธารณะ + ผู้ใช้แจ้ง | ดึงสถานะจริงจากหน่วยงานที่อนุญาต |
| ผลที่แสดง | "น่าจะมีสิทธิ์" + อัตราตามประกาศ | "ยืนยันจากหน่วยงาน" (`reportedBy: external`) |
| ข้อกำหนด | ทำได้ทันที | ข้อตกลงกับหน่วยงาน, DPIA, งานความปลอดภัย, แก้ requirements ข้อ 9 |
| ใช้ในการแข่ง | ใช้จริง | แสดงเป็นแผนในสไลด์ ไม่ทำหน้าจอจำลองที่ทำให้เข้าใจว่าเชื่อมรัฐได้แล้ว (requirements ข้อ 6) |

ไม่ต้องทำสองแอป ใช้โครงที่มีแล้ว:
- feature flag `govConnected` ใน app-config ปิดไว้
- port ใหม่ `eligibility` มี adapter `public_rules` (โหมด 1) และ `gov_api` (โหมด 2 วางแผน)
- Task มี `reportedBy: external` เตรียมไว้แล้ว

## 5. PDPA (พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562)
ผมไม่ใช่ทนาย ข้อด้านล่างเป็นแนวปฏิบัติทั่วไป ต้องให้ผู้รู้กฎหมายตรวจก่อนใช้จริง

| เรื่อง | ทำใน mock แล้ว | ต้องแก้ใน API |
|---|---|---|
| ประกาศความเป็นส่วนตัว (ใครเก็บ เก็บอะไร ใช้ทำอะไร ส่งให้ใคร เก็บนานเท่าไหร่ สิทธิ์) | ✓ ร่างในแอป มีเลขฉบับ | `GET /v1/privacy/notice` คืนข้อความและฉบับ |
| ยินยอมแยกตามวัตถุประสงค์ ไม่บังคับรวม | ✓ จำเป็น 1 ข้อ เลือกได้ 3 ข้อ (ตำแหน่ง, AI, แจ้งเตือน) | `Consent.purposes` แยกรายข้อ |
| ปฏิเสธแล้วยังใช้ได้บางส่วน | ✓ ดูโอกาสโดยไม่บันทึกข้อมูล, ไม่ยอม AI ใช้แบบเลือกเอง, ไม่ยอมตำแหน่งเลือกเขตเอง | server ต้องเช็คก่อนใช้แต่ละวัตถุประสงค์ |
| ถอนได้ง่ายเท่ากับให้ มีผลทันที | ✓ แท็บ ฉัน > จัดการความยินยอม | `POST /v1/me/consents` แบบ accepted=false รายข้อ |
| ประวัติความยินยอม | ✓ | `GET /v1/me/consents` |
| อายุ (ต่ำกว่า 20 ต้องมีผู้ปกครองยินยอม) | ✓ ช่องยืนยันก่อนกดยอมรับ | เก็บ `ageConfirmed` |
| ส่งข้อมูลไปต่างประเทศ (ผู้ให้บริการ AI) | ✓ แจ้งในข้อ AI และในประกาศ | AI port ไม่ส่งข้อมูลถ้าไม่ได้ยินยอม ใช้กฎแทน |
| ดู ขอสำเนา ลบ | ✓ | มีแล้ว (`/v1/me/export`, `DELETE /v1/me`) |
| เปลี่ยนฉบับประกาศแล้วถามใหม่ | ยังไม่ทำ | `app-config` ส่ง `noticeVersion` แอปถามใหม่เมื่อไม่ตรง |
| ระยะเวลาเก็บ, ผู้ติดต่อ/DPO | ยังไม่กำหนด | Owner ต้องกำหนด |
| เลขบัตรประชาชน | ไม่เก็บ | โหมด 2 ถ้าใช้ ThaID ต้องทำ DPIA และไม่เก็บเลขเองถ้าไม่จำเป็น |

## 6. Owner ตัดสินแล้ว
- แอปเดียว โหมดเชื่อมรัฐ (ThaID / ทางรัฐ) ซ่อนไว้หลัง feature flag `govConnected` ปิดเป็นค่าเริ่มต้น เชื่อมได้ก็มีข้อมูลยืนยัน เชื่อมไม่ได้แอปก็ใช้ได้ครบ
- แอปต้องไม่เป็นแค่เช็คสิทธิ์แล้วพาลิงก์ไปที่อื่นแบบทางรัฐ ต้องบอกได้ว่า **เงินอยู่ที่ไหน ได้เท่าไหร่ และไปเอามาอย่างไรให้จบ**

## 7. หน้าบ้านที่ทำตามการตัดสินใจ (mock)
- หน้าแรก: การ์ด "เงินที่คุณอาจได้" รวมต่อเดือนและครั้งเดียว บอกว่าประมาณหรือยืนยันแล้ว
- หน้า "เงินของฉัน": จัดกลุ่ม ยืนยันจากหน่วยงาน / น่าจะมีสิทธิ์ / ต้องเช็คยอดจริง / ตอบอีกข้อเดียว / ไม่น่ามีสิทธิ์
- หน้า "เส้นทางรับเงิน" 5 ขั้น: เงินอยู่ที่ไหนและได้เท่าไหร่ → มีสิทธิ์ไหม (ถามเฉพาะข้อที่ขาด แล้วคิดใหม่ทันที) → เตรียมเอกสาร → ไปยื่นที่ไหน (ออนไลน์ / สำนักงานใกล้บ้าน / โทร / ข้อความทวงนายจ้าง) → หลังยื่นเงินเข้าอย่างไรและถ้าไม่ผ่านทำอะไร → ปุ่มเริ่มรับเงินที่สร้างแผนทีละขั้น
- โหมดเชื่อมรัฐ: ซ่อนทั้งหมดเมื่อปิด เปิดแล้วมีจุดเข้า 3 ที่ (หน้าเงินของฉัน, เส้นทางรับเงิน, แท็บ ฉัน) มีความยินยอมแยกข้อ `gov` และติดป้ายชัดว่าเป็น DEMO / MOCK จนกว่าจะเชื่อมจริง

## 8. ยังเปิดอยู่
1. requirements ข้อ 9 ยังเขียนว่าการยืนยันตัวตนและการเชื่อมฐานข้อมูลสิทธิ์ของรัฐเป็น Deferred การตัดสินใจนี้ทำให้กลายเป็น "โหมดเสริมที่ปิดไว้" Owner ต้องปรับข้อความใน requirements เอง
2. เกณฑ์ อัตรา เอกสาร และช่องทางใน mock เป็นตัวอย่างทั้งหมด ต้องหาแหล่งจริงที่อ้างอิงได้ก่อนใช้
3. ระยะเวลาเก็บข้อมูล และช่องทางติดต่อเรื่องข้อมูลส่วนบุคคล
