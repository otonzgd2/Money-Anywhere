# การเลือกฐานข้อมูลของโครงการ Money Anywhere (มุมธุรกิจ)

**สถานะ:** ข้อเสนอ ยังไม่ใช่การตัดสินใจ ตามส่วนที่ 7 ของ requirements ต้องตัดสินในขั้นออกแบบของ AI-DLC และบันทึกเป็น ADR ใหม่ พร้อมให้เจ้าของโครงการอนุมัติ
**เอกสารที่เกี่ยวข้อง:** [knowledge-database-approach.md](../product/knowledge-database-approach.md), [requirements.md](../product/requirements.md), [adr-001-stack.md](../design/adr-001-stack.md), [backend.md](../design/backend.md)

## 1. สถานะปัจจุบัน

- ไม่มีฐานข้อมูลจริง ระบบเก็บสถานะใน memory (`Map`) ของ `contracts/mock-server.js`
- Port `store` (`contracts/adapters/store.js`) มี 2 โหมด
  - `memory`: ไม่ตั้ง `DATA_FILE` ข้อมูลหายเมื่อ restart ใช้ตอนรัน contract test
  - `file`: ตั้ง `DATA_FILE` เขียน snapshot เป็นไฟล์ JSON ไฟล์เดียวแบบ atomic
- Interface มีแค่ `load()` และ `save(snapshot)` ใน `package.json` ของ `contracts/` ไม่มี dependency ของฐานข้อมูล
- โค้ดใน `store.js` ระบุแผนเพิ่ม Postgres adapter (JSONB หนึ่งแถวต่ออุปกรณ์)

## 2. ความต้องการทางธุรกิจที่ฐานข้อมูลต้องรองรับ

มาจากเอกสาร `knowledge-database-approach.md`

| # | ความต้องการ | ที่มา | ผลต่อการเลือก DB |
|---|---|---|---|
| 1 | ทุกรายการมีแหล่งที่มา วันที่ตรวจ และสถานะ | FR-03, FR-08 | ต้องมีคอลัมน์และการกรองตาม `status`, `last_verified`, `source_url` |
| 2 | ทะเบียนแหล่งข้อมูล (สิทธิ์เก็บ แสดงซ้ำ ใช้เชิงพาณิชย์) | ความเสี่ยงข้อ 1 | ตารางแยกพร้อม relation กับรายการความรู้ |
| 3 | อัปเดตแบบ incremental ด้วย `content_hash` และคิวตรวจโดยคน | ส่วน 5.5 | ต้อง upsert รายเรคคอร์ดและค้นหาตามแฮชได้ ไม่ใช่เขียนทั้ง snapshot |
| 4 | ประวัติเวอร์ชันของรายการ ย้อนดูได้ | ส่วน 5.5 ข้อ 6 | ตารางเวอร์ชัน |
| 5 | ซ่อนรายการที่เลย `deadline` อัตโนมัติ | ส่วน 5.5 ข้อ 5 | query ตามช่วงเวลา |
| 6 | แยกฐานความรู้ออกจากข้อมูลผู้ใช้ | ความเสี่ยงข้อมูลส่วนบุคคล | สองที่เก็บ หรือสอง schema |
| 7 | ผูกหลักฐานกับ commit ทดสอบซ้ำได้ | AC-05 | สร้างฐานจาก migration และ fixture ได้เหมือนกันทุกเครื่อง |
| 8 | ค้นโอกาสตามพื้นที่บนแผนที่ | `backend.md` | ภายหลังอาจต้องใช้ PostGIS |

ขนาดข้อมูลช่วง MVP: ความรู้ประมาณ 10–20 รายการต่อหมวด (10 หมวด) และข้อมูลจำลอง 77 รายการ ปริมาณเขียนต่ำ

## 3. ปัจจัยตัดสินใจ

| ปัจจัย | น้ำหนัก | เหตุผล |
|---|---|---|
| ตั้งค่าและใช้ง่ายสำหรับทีม 3 คนบน Windows | สูง | ไม่มีคนดูแลระบบเฉพาะ ลดเวลา setup |
| ต้นทุน | สูง | ยังไม่มีงบที่ตกลง (ส่วน 8 ของเอกสารแนวทาง) |
| ความสามารถ query (กรอง join ประวัติเวอร์ชัน) | สูง | ความต้องการข้อ 1–5 |
| ย้ายไปโฮสต์จริงได้โดยแก้น้อย | กลาง | ไม่ผูกกับผู้ให้บริการเร็วเกินไป |
| สอดคล้องกับ ADR-001 | กลาง | ลดการตัดสินใจซ้ำ |

## 4. ตัวเลือกที่เปรียบเทียบ

| ตัวเลือก | ข้อดี | ข้อเสีย | ความเหมาะสมตอนนี้ |
|---|---|---|---|
| ไฟล์ JSON (ปัจจุบัน) | ไม่มี dependency เปลี่ยนง่าย | เขียนทั้ง snapshot ค้นหาและเก็บประวัติเวอร์ชันไม่ได้ | พอสำหรับสถานะผู้ใช้ช่วง Demo ไม่พอสำหรับฐานความรู้ |
| **SQLite** | ไม่ต้องมี server เป็นไฟล์เดียว SQL เต็มรูปแบบ มี JSON function ฟรี | เขียนพร้อมกันหลายตัวไม่ได้ ไม่เหมาะกับโฮสต์ที่ไม่มี disk ถาวร | **เหมาะที่สุดตอนนี้** |
| PostgreSQL (ในเครื่อง) | JSONB, PostGIS, ใช้ต่อบน production ได้ | ต้องติดตั้งหรือใช้ Docker เพิ่มภาระช่วงต้น | เหมาะระยะ 2 ขึ้นไป |
| PostgreSQL บนคลาวด์ (RDS/Aurora, Neon, Supabase) | จัดการให้ รองรับหลาย instance | มีค่าใช้จ่ายหรือข้อจำกัด free tier (Render Postgres ฟรีหมดอายุใน 30 วัน ตาม ADR-001) | เป้าหมายตอนขึ้นใช้จริง |
| DynamoDB | ตรงกับ AWS ไม่ต้องดูแล server | ต้องออกแบบ key ตาม access pattern กรองตามสถานะ แฮช และ deadline ลำบาก ไม่มีประวัติเวอร์ชันในตัว รันในเครื่องต้องใช้ DynamoDB Local | ไม่แนะนำสำหรับฐานความรู้ |
| MongoDB / Redis | ยืดหยุ่น | ไม่ตรงกับ use case เพิ่ม dependency | ไม่แนะนำ |

## 5. ข้อเสนอ

ใช้ **SQLite** ตอนนี้ แล้วย้ายไป **PostgreSQL** เมื่อถึงเงื่อนไขด้านล่าง

เหตุผลหลัก
- สอดคล้องกับระยะ 1 ถึง 2 ในส่วน 6 ของเอกสารแนวทาง และ ADR-001 ที่เสนอ "ไฟล์ JSON หรือ SQLite" ช่วง Demo
- ไม่เพิ่มภาระติดตั้งหรือค่าใช้จ่าย ทีมได้ฐานข้อมูลเหมือนกันทุกเครื่อง
- ตอบความต้องการข้อ 1–5 และ 7 ได้ด้วย SQL (upsert, query ตามสถานะ/deadline, ตารางเวอร์ชัน, migration)
- ปริมาณข้อมูลและการเขียนช่วง MVP ต่ำ อยู่ในขีดความสามารถของ SQLite

เงื่อนไขย้ายไป PostgreSQL
- ต้องรันบน AWS หรือโฮสต์ที่ไม่มี disk ถาวร
- มีหลาย instance เขียนพร้อมกัน หรือมีผู้ใช้จริง
- ต้องค้นตามรัศมีบนแผนที่ (PostGIS)
- ระยะ 3 ที่มีงานดึงข้อมูลอัตโนมัติและคิวตรวจ ซึ่งต้องการการเขียนพร้อมกัน

## 6. แนวทางสถาปัตยกรรมที่รองรับการย้าย

1. แยกฐานความรู้ออกจากข้อมูลผู้ใช้ตามความเสี่ยงด้านข้อมูลส่วนบุคคล
2. สถานะผู้ใช้ต่ออุปกรณ์ใช้ port `store` เดิม ส่วนฐานความรู้เพิ่ม port แบบ repository (เช่น `knowledge` มี `upsert`, `findByStatus`, `listVersions`) เพราะ `load/save snapshot` ไม่เหมาะกับการอัปเดตรายเรคคอร์ด
3. ตารางที่ต้องมีเบื้องต้น: `knowledge_item` (ฟิลด์ตามส่วน 5.3 ของเอกสารแนวทาง), `knowledge_item_version`, `source_register` (ส่วน 5.4), `review_queue`
4. ใช้ SQL มาตรฐานและเก็บฟิลด์ยืดหยุ่นเป็นคอลัมน์ JSON เพื่อย้ายไป JSONB ได้โดยแก้ adapter ที่เดียว
5. Migration เป็นไฟล์ `.sql` เรียงเลข และมีสคริปต์โหลด `contracts/fixtures/` เข้าฐาน

## 7. ความเสี่ยงและข้อควรระวัง

| ความเสี่ยง | แนวทาง |
|---|---|
| ไฟล์ SQLite หายบนโฮสต์ที่ไม่มี disk ถาวร | ใช้ SQLite เฉพาะการพัฒนาและ Demo ในเครื่อง ขึ้นโฮสต์จริงใช้ Postgres |
| การค้นข้อความภาษาไทย (SQLite FTS5 และ Postgres ตัดคำไทยเองไม่ได้) | ตัดคำที่ฝั่ง Node ก่อน หรือใช้ตัวช่วยเพิ่ม ตัดสินเมื่อมีความต้องการค้นข้อความจริง |
| สิทธิ์ในการเก็บและแสดงซ้ำของแหล่งข้อมูล (ความเสี่ยงสำคัญที่สุด) | ทำทะเบียนแหล่งข้อมูลและตรวจข้อกำหนดก่อนนำข้อมูลเข้าฐาน ฐานข้อมูลที่เลือกไม่ช่วยลดความเสี่ยงนี้ |
| ข้อมูลส่วนบุคคลรั่ว | เก็บให้น้อยที่สุด แยกฐาน ใช้โปรไฟล์สมมติตอนสาธิต |
| เลือกเทคโนโลยีก่อนผ่าน AI-DLC | บันทึกเป็น ADR และขออนุมัติก่อนลงมือ |

## 8. สิ่งที่ยังไม่ทราบและต้องตัดสิน

- เวอร์ชัน Node.js ของทีม (กำหนดว่าจะใช้ `node:sqlite` ที่ต้อง Node 22.5 ขึ้นไป หรือ `better-sqlite3`)
- งบประมาณและผู้ดูแลระบบหลังการแข่งขัน (ต้องถามเจ้าของโครงการ)
- ที่โฮสต์ปลายทาง (AWS, Render, Supabase หรืออื่น) ซึ่งกำหนดเวลาที่ต้องย้ายไป Postgres
- ระยะเวลาเก็บข้อมูล (open-items O1) และข้อกำหนดด้านกฎหมายข้อมูลส่วนบุคคล (PDPA)
